# Contributing to Marktyp

Thank you for your interest in contributing to Marktyp.
This project is open source and every contribution is welcome, but to maintain quality and consistency please follow these guidelines.

---

## Philosophy

The project prioritizes:

- simplicity over premature abstraction
- clarity over "clever code"
- explicit behavior over magic
- small iterative changes

If a solution is difficult to explain, it is probably too complex.

> [!CAUTION]
> **AI disclaimer**
>
> We are strong supporters of automated programming tools and we use a wide variety of them. This does not mean that we allow AI agents to make every change without intervention: we strive for the intelligent use of these tools and we are firmly committed to performing human code reviews. For this reason, we ask you to contribute clear, atomic code that can be explained by the contributor themselves.

## How to contribute

1. Open an issue before working on:

    - new features
    - architectural changes
    - important refactors

    For small bug fixes you can open a pull request directly.

    > If you do not necessarily want to wait for the triage phase, you can start working on it and submit a pull request.

2. Fork and branch:

    - Fork the repository.
    - Create a descriptive branch from the related GitHub issue.
    - Never work directly on `main`.

3. Code and tools:

    - Write clear and moderately commented code.
    - Preserve Marktyp's local Markdown format and existing behavior.
    - Keep the Wails RPC facade thin and place domain logic under `internal/`.
    - Keep frontend state and operations in `frontend/src/lib/stores/` and focused UI in `frontend/src/lib/components/`.
    - Use [Semantic Versioning](https://semver.org/) for releases.

## Development setup

Marktyp requires Go `1.26.1+`, Node.js `20.19+`, npm, and the Wails CLI `v2.15.0`.

```bash
git clone https://github.com/raml-dev/marktyp.git
cd marktyp
go install github.com/wailsapp/wails/v2/cmd/wails@v2.15.0
cd frontend
npm ci
cd ..
```

Run the application locally with:

```bash
wails dev
```

Do not edit files under `frontend/wailsjs/` by hand. They are generated by Wails.

## Skills and guidelines

This project includes operational guidelines in `AGENTS.md`. They are useful as a reference even when you are not using AI-assisted development tools.

In particular:

- preserve the existing branding, themes, and Document, Source, and Dual modes
- do not add dependencies without discussing them first
- keep business logic and IPC out of presentation components
- protect unsaved edits from asynchronous races
- keep persisted data backward compatible

## Commits

Write clear and descriptive commits, for example:

- `feat(editor): add a formatting action`
- `fix(notes): preserve the active draft`
- `refactor(export): isolate PDF rendering`

Avoid generic commits such as:

- `fix`
- `update`
- `various changes`

Always identify the affected component or functionality.

## Pull requests

When opening a pull request:

- describe what it does
- explain why the change is needed
- keep it as small and atomic as possible
- include screenshots for visible interface changes
- mention any behavior that could not be verified locally

We may ask for a large pull request to be split into multiple smaller ones.

> [!NOTE]
> **Golden rule:** if you cannot clearly explain the change in the description, the pull request is probably too complex.

## Triage

Issues and pull requests are evaluated during triage. This process may affect the state and progress of a contribution.

If a contribution does not fully follow these guidelines, we may ask for additional context or changes before proceeding.

> [!NOTE]
> This does not necessarily mean the pull request will be closed, but it may affect review and merge timelines.

We aim to provide clear and constructive feedback whenever possible.

## Tests

Do not break existing tests, and add regression tests for bug fixes and new behavior when applicable.

Run the complete verification suite before opening a pull request:

```bash
go test ./...
go test -race ./...
go build ./...
cd frontend
npm run format
npm run check
npm run lint
npm run build
npm test
cd ..
wails build
```

Avoid monkey patching in tests, as it introduces hidden behavior and reduces clarity.

## Security issues

If you find a vulnerability, do not open a public issue. Contact the project maintainers privately through the raml-dev organization so that the problem can be investigated before details are disclosed.
